How Purposea evaluates a vacancy

Every vacancy that enters the pipeline is tested against your filters first, then evaluated by a language model against your profile. This page documents the sequence — the contracts between stages, the failure modes, and the trade-offs that shaped the current design.

The work happens in two passes: a deterministic filter pass that's cheap to run and produces stable results, and a semantic pass that evaluates anything the filter pass let through. By the time you see a match in your inbox, it has been through both.

The filter pass

Filters run before AI evaluation. If a vacancy doesn't pass, Purposea never evaluates it — which means filter changes don't retroactively re-run history. This is intentional: the cost would be prohibitive and the value low (people care about what's coming, not what they missed two months ago).

Some filters are hard; others are advisory. The seniority floor is hard. Keyword exclusions in titles are hard. Keyword exclusions in JD bodies are advisory — they reduce score rather than reject outright. See the filter taxonomy reference for the full list.

Filter changes are not retroactive

If you tighten your seniority floor today, vacancies evaluated yesterday stay in your inbox at their original tier. Only future evaluations reflect the new floor.

The semantic pass

Vacancies that pass filters are evaluated by an LLM against the user's profile. The model returns a tier (Strong / Good / Possible / Excluded) plus a one-paragraph reasoning. The reasoning is what the user actually reads — the tier just controls whether the email shows it.

Scoring

Tiers map to score bands:

TierScore bandAvg per weekSurfaced where
Strong0.85 – 1.003Email + Inbox
Good0.65 – 0.845Email + Inbox
Possible0.45 – 0.648Inbox only
Excluded0.00 – 0.4422Excluded review only

The model that generates the reasoning is not the same as the one that produces the score — score is a cheaper rubric model, reasoning runs on the headline model. This separation lets us re-score quickly when the rubric changes without paying for a full reasoning regen.

Implementation

The evaluation function takes a profile and a vacancy, returns a tier and reasoning:

async def evaluate(
    profile: Profile,
    vacancy: Vacancy,
) -> EvaluationResult:
    # filter pass first — cheapest possible reject path
    if not filters.passes(profile, vacancy):
        return EvaluationResult(tier="excluded", score=0.0)

    # rubric model — ~30ms, ~$0.0001/call
    score = await rubric.score(profile, vacancy)

    if score < 0.45:
        return EvaluationResult(tier="excluded", score=score)

    # reasoning model — ~3s, ~$0.01/call
    reasoning = await reasoner.explain(profile, vacancy)
    tier = tier_of(score)

    return EvaluationResult(tier=tier, score=score, reasoning=reasoning)
Two-stage evaluation cut weekly compute by 78%

By rejecting at the rubric stage, only 38% of filter-passing vacancies reach the reasoner. That's the difference between this being financially viable as a digest product and not.

Rubric drift

The rubric model is replaced quarterly; we re-score the last 30 days of evaluations to detect tier flipping. If >5% of vacancies flip up or down, the new rubric is rejected and we investigate.

Trade-offs

"The right architecture is the one that makes your most expensive operation rare and your most common operation cheap." — engineering principle, internal handbook

Every architectural decision in the pipeline is downstream of one observation: vacancies are mostly not relevant. A typical user filters and rejects more than 90% of weekly inbound. Designing for that reality means:

  1. Reject early, reject cheaply. Filters before LLMs. Rubric before reasoning.
  2. Make the kept ones legible. Every surfaced match has a reason, not just a score.
  3. Never paywall the explanation. If a vacancy reaches the user, the reasoning reaches the user.
